01 · Security principles & disclosure rules

The governing rule

The interface never weakens a backend security property to produce a more helpful screen. Where the data model deliberately withholds a fact, the gate withholds it too — even when that makes the message less satisfying, and even when a support ticket would be shorter if we said more.

The corollary matters as much: where the backend does not withhold a fact, hiding it is not security, it is discourtesy. A person removed from a workspace they used yesterday already knows it existed. Telling them the date and the actor discloses nothing they could not infer, and saves a support conversation.

SG-01 · gates 08 and 09 One screen, two causes
FS Fortune Signora
This invitation link cannot be used

If you already have a Signora account, sign in and the workspace will appear if you have been added to it. Otherwise, ask the person who invited you to send a new invitation.

Sign in Go to signora.com
req_8d40-1c7b Quote this to support
No organisation name, no inviter, no address, no cause. The screen is identical whether the token never existed, was already consumed, expired outside its grace window, or is valid for a different identity.

Why this screen is deliberately unhelpful

The invitation endpoint takes an unauthenticated token from anyone on the internet. Any variation in its response — wording, latency, status code, page size — turns it into an oracle for testing whether an address belongs to a Signora customer.

The one exception, and its condition
A token that is valid, unconsumed and addressed to the currently signed-in identity is not a gate at all — it is an acceptance, owned by Team Management. SG-01 is reached only when that test fails, and it never explains which part failed.
